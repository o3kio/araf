# M3 — Rust BFF boundary and deterministic O3K contract harness

**Delivery gate:** Prototype  
**Depends on:** M0

## Goal

Establish the server/client boundary that the prototype can use with deterministic fixtures and the MVP can later bind to real O3K without rewriting frontend semantics.

## Architectural constraints

- Follow `AGENTS.md` and the accepted ADRs.
- Araf must not invent authoritative O3K cloud semantics or undocumented production endpoints.
- Fixture behavior must remain explicitly separated from production adapters.
- Tenant/provider/operator trust and vocabulary boundaries must remain intact.
- Implement only this phase; post-MVP features remain out of scope unless this issue explicitly requires a compatibility hook.

## Full implementation prompt

Use [`prompts/M3-bff-contract-harness.md`](../blob/main/prompts/M3-bff-contract-harness.md) as the implementation instruction and acceptance source of truth.

## Acceptance criteria

- both BFFs expose independent fixture APIs,
- 100k-total collection proof remains bounded per request,
- action returns Operation rather than fake synchronous success,
- cross-scope/route negative fixture tests exist,
- frontend API contract is typed,
- no undocumented O3K endpoint has been invented.

## Required final evidence

The PR must contain the implementation report required by `AGENTS.md`, including tests, security/accessibility implications, upstream O3K gaps and explicitly deferred scope.
