# P3.1 — Freeze CloudBackend architecture and compatibility semantics

## Goal
Introduce the minimum backend abstraction that lets Araf support O3K and OpenStack without turning the frontend into backend-specific branches or degrading the O3K model.

## Required design work
- inspect current Araf BFF/resource client boundaries;
- define `CloudBackend`-equivalent server-side traits/contracts for identity, scopes, discovery, resources, actions, operations, governance and usage;
- extract current O3K behavior behind an `O3kBackend` without changing observable O3K semantics;
- define backend capability/provenance identity;
- define error normalization without hiding backend-specific diagnostics;
- define OpenStack CompatibilityOperation semantics, persistence/reconciliation and distinction from canonical O3K Operation;
- define token/credential ownership and isolation;
- define configuration selecting one backend for first release;
- add an accepted ADR before broad adapter implementation.

## Forbidden
No `if openstack` branches scattered in React, no least-common-denominator rewrite of the generic resource model, no multi-cloud aggregation scope creep.

## Acceptance
Current O3K E2E remains green through the new boundary and the ADR is sufficiently precise for independent P3.2-P3.8 implementation.
